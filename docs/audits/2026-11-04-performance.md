# TyLog performance audit — 2026-11-04

What this repo does: TyLog is a local-first Flutter research logbook backed by Typst vault files, a Dart core and an Android Storage Access Framework (SAF) bridge. This audit assumes 10,000 indexed notes including 5,000 dailies. Task, suggestion and asset counts are stated separately: note count alone does not determine them.

Counts below are code-derived estimates, not device timings. P0 means unusable or data-threatening in ordinary use; P1 means likely major interactive stall at the stated scale; P2 means material conditional cost; P3 means smaller or infrequent cost. No P0 is established by this static audit.

## Measurement setup

Use a disposable 10k-note fixture with 5k dailies and representative links, tasks, sidecars and image sizes; vary the parameter named in each finding. Compare app-local storage and a selected SAF tree on the same phone. Capture DevTools root-isolate CPU and Flutter build/raster frame timings, including p95, p99 and frames over the display budget; record action latency, Dart heap and Android PSS. Count Dart platform-channel operations separately from native ContentResolver queries and stream opens. Instrument a profiling branch or counting fixture without logging private content. Repeat cold and warm runs and report device, build, fixture and sample count.

Use a release-signed profile build with the production package only when the matching keystore is available. Integration drive must use the isolated optional .profiletest suffix. For cold start enlarge logcat to 16 MB, force-stop org.tylog.tylog, wait a few seconds, then start it and collect TYLOG_STARTUP marks and stage timings. Android gfxinfo decor timings do not establish Flutter jank.

## Must fix

1. **P1 — Board ordering is quadratic and cards are eagerly laid out.** lib/widgets/entity_board.dart:514–527 and :573–590 filter by column, then call firstWhere for every ordered ID. A column with 5,000 tasks can do about 12.5 million ID comparisons per rebuild; one IntrinsicHeight/Column constructs and lays out all cards and drag targets. Fix: map IDs to tasks once, group by status once, and use a lazy sliver or builder with position-aware drop targets. Measure: open a board with 100, 1,000 and 5,000 tasks in one column, drag and release a card, and record build/layout CPU and frame percentiles.

2. **P1 — Incoming's seven-result limit does not limit work.** lib/app_mobile/enrich_flow.dart:410–450, :463–490 and :763–767 recursively list and sort all sidecars, then read days sequentially until seven nonempty results are found. Empty, stale or already resolved days do not count. With 5,000 daily sidecars and no actionable suggestions, opening can inspect all 5,000: up to 5,000 mention exists calls, 5,000 mention reads and 5,000 note reads, plus listing and possible shown-ledger writes; missing paths and the currently open day reduce that count. Every decision and Show older reloads the queue. Fix: bound days examined, retain a cursor and accumulated results, and maintain an incremental actionable-sidecar summary with correct invalidation. Measure: count channel methods, provider queries and opens and time sheet readiness for 0%, 1% and 100% actionable sidecars; repeat after a decision and Show older.

3. **P1 — Mention matching scans every candidate for each mention on the UI isolate.** lib/app_mobile/enrich_flow.dart:125–143 and packages/tylog_core/lib/src/enrich.dart:415–466 show that the ten-minute memory cache avoids repeated normalization but candidate matching still tests eligible entities per mention. At 10,000 eligible entities and 20 mentions this is up to roughly 200,000 entity matches per day; seven such days approach 1.4 million, before scoring. The marker function also builds a 10,000-entry ID map for each uncached application even when there are no markers (enrich.dart:761–768). Fix: cache inverted normalized-name/word indexes and the ID map in EnrichMemory, preserve matching precedence, and move remaining large computation off the root isolate where practical. Measure: capture TYLOG_ENRICH, root CPU and frame timing for 1/20/100 mentions and 1k/10k eligible pages, including Incoming and a changed daily. The historical 562-second A24 case in docs/plans/activity-plan.md:430 predates normalization caching and is not a current measurement.

4. **P1 — Journal repeatedly sorts the entire daily index while scrolling.** lib/widgets/journal_feed.dart:105–109, :150–165, :174–180 and :195–204 call _days in build, scroll callbacks and post-frame bootstrap, including callbacks where no day is added. Each call scans 10k notes and sorts 5k dailies, on the order of 60k comparisons. Fix: cache the sorted list by index identity or revision and reuse it for build, scrolling and bootstrap. Measure: fling the 5k-day fixture, count _days calls, record root CPU and p95/p99 frames, and verify index changes invalidate the cache.

## Should fix

5. **P2 — Journal task rows repeatedly search the whole task index.** lib/widgets/journal_feed.dart:288–301 searches index.tasks from the start for every rendered task. With 10,000 indexed tasks and 30 visible rows this can perform up to 300,000 comparisons per rebuild. Fix: maintain a (notePath, taskId) lookup per index. Measure: render a daily with 10/100 tasks against 1k/10k indexed tasks, then rebuild and scroll while sampling CPU and frames.

6. **P2 — Entity timeline recomputes vault-wide work even when collapsed.** lib/widgets/entity_timeline.dart:35–37 and :53–105 construct a resolver from all notes, scan all tasks including text regex matches, and sort matching entries before checking whether the timeline is expanded. At 10k notes and 10k tasks, each build repeats resolver construction and 10k task checks; popular entities also sort thousands of entries. Display rows are lazy. Fix: reuse the workspace resolver, index task references by entity, and memoize sorted entries by entity and index revision; defer work while collapsed if the count can be computed cheaply. Measure: open, expand and rebuild an entity with 0 versus 5k backlinks and 10k tasks, capturing root CPU and frames.

7. **P2 — Incoming re-reads complete ledgers twice per refresh and eagerly creates rows.** lib/app_mobile/enrich_flow.dart:463–475 and :523–542, packages/tylog_core/lib/src/attention.dart:98–130, and lib/review_queue.dart:74–102 and :140–157 show two loadDecisions calls per queue load. Each lists decision, feedback and shown directories and reads every device ledger, even though OCR and audio need only their own decision IDs. It also reads every audio JSON and mount rows file and builds all health, audio and OCR widgets in a ListView children list. With D decision, F feedback, S shown files, A audio files and M mounts, these loaders make at least 2*(3+D+F+S)+1+A+2*M Dart storage operations when files exist, excluding health, enrichment and native resolution queries. One thousand audio files means 1,000 sequential reads each refresh. Fix: load only required decision sources once, update queue state after actions, paginate sidecars and rows, and build sections lazily. Measure: count operations and time open and rejection with 10/1,000 audio files and increasing ledger size; inspect heap and frame time with 1,000 health findings. Health reads only the latest report (lib/review_queue.dart:23–39).

8. **P2 — Duplicate merge preview reads every note sequentially.** lib/workspace_note_merge.dart:56–75, :83–86 and :142–154 reads and scans all indexed notes to detect supported and unsupported references, not only backlinks. At 10k notes this is approximately 10k note reads and the total note bytes scanned on the root isolate; changed text is retained in before/after maps. Fix: build a complete reference and unsupported-reference candidate index during background indexing, or run exhaustive verification in a cancellable worker with bounded reads and visible progress; preserve unsupported-reference and concurrent-change checks. Measure: preview a merge with few backlinks on app-local and SAF fixtures; count reads/bytes, time, root CPU and heap, and confirm an unsupported reference outside backlinks still blocks. The duplicate finder itself is linear in names and aliases (packages/tylog_core/lib/src/enrich.dart:40–55), though its page repeats normalization on rebuild (lib/widgets/settings/maintenance_page.dart:158–161).

9. **P2 — GitHub mount refresh buffers a complete archive and makes large transient copies.** lib/github/github_client.dart:109–120, :172–175 and lib/github/mount_fetcher.dart:90–98, :149–195 download a changed ZIP into memory up to 200 MiB, then extract in an isolate; hashing creates a list containing the entry bytes. Extracted input is capped at 500 MiB and each entry at 20 MiB, still allowing substantial transient memory and GC. Synchronous extraction runs in the worker isolate, not on the UI isolate. Fix: stream download to a temporary file, use file-backed extraction and incremental Git blob hashing without list spread; preserve validation and atomic swap. Measure: refresh a changed 10k-file mount with 20/100/200 MiB compressed archives; record PSS, heap by isolate, GC, wall time and Flutter frames. The six-hour automatic throttle and unchanged-SHA fast path already limit unchanged refreshes.

10. **P2 — SAF directory walks and cold path resolution amplify per-file work.** android/app/src/main/kotlin/org/tylog/tylog/SafBridge.kt:605–615, :659–672, :676–719 and :806–837, plus lib/vault_storage.dart:123–157: a recursive listing queries each visited directory and returns all entries over one channel call; only recursive root listings use the listing cache. A cold unresolved path walks components with child queries that scan siblings; a full walk warms URI entries. Five thousand sidecars in one directory imply one directory query returning 5,000 rows; 5,000 directories imply roughly 5,000 directory queries. Fix: retain correct directory invalidation, use paged or targeted application indexes for review, and avoid redundant exists-before-read calls; retain external-change verification. Measure: count channel calls, queries, rows and opens for cold/warm Incoming and full scan on flat versus nested 10k-note trees, including an externally changed file. Verification and patching at :723–803 add directory- and dirty-set-dependent work.

11. **P2 — Startup fast path waits for every vendored package file.** lib/workspace_controller.dart:763–814 and :850–883 walk all _system/packages directories and read files serially before today-readable and fast-path-done, then read managed files and support data. Leading-slash and plain keys share each byte buffer. Cost depends on package count and bytes, not note count: 1,000 files mean 1,000 reads plus directory listings before the editor is published. Fix: publish the editor once required resources are ready and load optional package contents lazily or in a background phase, preserving compile readiness and vault-switch cancellation. Measure: cold start with 0/100/1,000 vendored files; record startup marks, channel/query counts, first usable editor and memory. Production indexing already runs in a worker after the fast path (:827–831). Historical P30 no-change walk 5–6 s and worker scan 9–10 s are in docs/audits/2026-10-16-sync-indexing.md; these are not new measurements.

12. **P2 — Journal source cache grows with browsing history.** lib/widgets/journal_feed.dart:57–58, :82–87 and :215–224 retain every opened daily's completed source future until vault change or widget disposal. Reading 5,000 dailies of 10 KiB each retains about 49 MiB of source payload alone, plus strings, futures, views and images; normal short sessions retain less. Fix: use a bounded LRU of source futures, evict off-screen days and invalidate on note changes without discarding visible edits. Measure: browse 50/500/5,000 days, take heap snapshots after GC, then leave the screen and compare retained strings; track PSS and Flutter image cache separately.

13. **P2 — Board rebuilds rescan all notes, tasks and issues.** lib/widgets/entity_board.dart:462–465 and packages/tylog_core/lib/src/board.dart:422–464 show tasksForEntity and issuesForEntity each rebuilding the parent-child map; the task path scans notes several times and all tasks. This occurs even when loading and after local busy or drag state changes. At 10k notes each rebuild performs multiple 10k-note passes plus task and issue scans regardless of the entity's size. Fix: compute shared hierarchy and lookup maps once per index revision, cache entity results until that revision changes, and group cards once. Measure: open and drag on a small entity board within 1k versus 10k notes while holding card count fixed; count builds and CPU time.

14. **P2 — Explicit index rebuild publishes progress to the whole workspace.** lib/workspace_controller.dart:2017–2024 and lib/vault_worker.dart:367–371: the worker throttles progress to one event per 100 records, but manual rebuild still calls global notifyListeners on each event. At 10k records that is around 100 notifications, potentially rebuilding expensive active screens during the scan. Fix: send progress through the existing narrow progress notifier and throttle by time, retaining completion and error notifications. Measure: rebuild a 10k-note fixture with Journal or an entity view mounted; count workspace notifications and widget builds, then compare frames. Routine silent refreshes do not take this progress branch.

15. **P2 — GitHub project columns eagerly instantiate every card.** lib/widgets/github_project_board.dart:118–157 filters all remote items for each column and builds a complete children list. Five columns and 5,000 project items require 25,000 status checks plus 5,000 card trees per rebuild; project size is separate from vault size. Fix: group items once and use ListView.builder per column. Measure: open and move an item in projects with 100/1,000/5,000 cards; record build/layout CPU, heap and frames, separately counting network requests.

## Nice to have

16. **P3 — Enrichment memory construction scales with vault links and feedback.** lib/app_mobile/enrich_flow.dart:76–90 and packages/tylog_core/lib/src/enrich.dart:294–359 build memory on the root isolate after reading complete feedback and shown ledgers. It scans notes and links and records co-occurrences. For a note with F features and E entity features, _observe visits up to E*F features; at 10k notes with ten features and five entity features each that is roughly 500,000 feature visits, plus resolver and ledger work. The ten-minute cache limits repeats, but a decision invalidates it (lib/app_mobile/enrich_flow.dart:150–175). Fix: incrementally update feedback state and construct/index memory in a worker, preserving deterministic ranking and vault-generation checks. Measure: compare cold and warm memoryMs logs, root CPU and heap for sparse versus highly linked 10k-note fixtures, then accept a suggestion and repeat.

Verdict: Fix board ordering and eager layout, bounded Incoming work, mention matching and Journal sorting first; validate each against device traces before assigning a millisecond budget.

Not checked: This is a static, targeted audit, not an exhaustive line-by-line review of every widget, sync transport, image decoder, native provider or database query. No profile build, integration test, benchmark or vault mutation was run; a connected device was detected but no workload was executed. The requested FIXLOG.md is absent from the repository. Engineering rules, Wave 21–24 plan history, sync-memory history and the prior sync/indexing audit were consulted. Historical fixed archive retention was not treated as a current defect. This audit does not establish a general per-keystroke quadratic path or a current image leak; image memory and real keyboard/IME behavior still need the fixture and acceptance work in CONTEXT.md.
