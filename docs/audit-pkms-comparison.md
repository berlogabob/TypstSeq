# PKMS competitive audit: Logseq OG vs Logseq 2.0 DB vs Tine vs TyLog

**Date:** 2026-08-20. **Sources:** `docs/research-logseq-og-features.md`, `docs/research-logseq-db-features.md`, `docs/research-tine-fork.md`, `docs/research-logseq-db-format.md` (all primary-source-cited; 12 claims spot-checked against cited URLs, all confirmed), `docs/research-tylog-features.md` (codebase-derived, TyLog v0.3.0+92).

## BLUF

The Logseq ecosystem split in 2026 into three diverging worlds, and none of them occupies TyLog's ground. **Logseq OG** (file-based) is officially maintenance-only and observably idle (~3 months without a commit; one release ever in its own repo) — its users are stranded on a frozen product. **Logseq 2.0 DB** is a genuine data-model upgrade (typed properties, classes, views, RTC sync) but shipped its beta with real regressions (whiteboards removed, SRS data not migrated, ~65 of several hundred plugins compatible) and a lock-in answer — the one-way, desktop-only Markdown Mirror — that concedes the plaintext complaint rather than resolving it. **Tine** is not a fork at all: it's a two-month-old, solo-maintainer, AI-assisted from-scratch rewrite (Rust/Tauri/SolidJS) that keeps Logseq's Markdown files byte-compatible and beats both Logseqs on speed and PDF handling, at the cost of no plugin ecosystem, no graph view, no SRS, no iOS, and high abandonment risk.

**TyLog's position:** it is the only one of the four with typed, compilable plaintext (Typst) as the storage layer — stronger structure than OG's `key:: value`-in-text, without the DB version's opaque SQLite — plus the only native typeset-PDF output, release-grade Android with real sync-conflict safety, and a task model (RRULE, reminders, time tracking) that matches or exceeds all three. Its real gaps against the field: no block references/transclusion, no query language, no plugin/extensibility story, and no SRS/whiteboards. The strategic takeaways: (1) OG's stranded users are an import-target audience TyLog already serves (file importer shipped, DB importer planned); (2) the field's weakest shared point — trustworthy mobile — is TyLog's strongest; (3) Tine proves demand for "fast, files-first, Logseq-compatible" — TyLog's differentiator on top of that demand is Typst typesetting and structured data that still compiles as text.

## How each is implemented (one paragraph each)

**Logseq OG.** ClojureScript + Electron/mobile shells; the OCaml `mldoc` parser reads md/org into an in-memory Datascript database rebuilt from files at startup — files are the source of truth, the DB is a disposable index. This buys total data ownership and git-ability, and costs startup/scale performance (officially tracked freezes at ~18k pages, ~300MB graphs), parse fragility (`key::` properties are text), and a corruption warning in the maintainers' own README.

**Logseq 2.0 DB.** Same CLJS app family, but datascript now *persists* into SQLite (`kvs` table, transit-encoded index nodes of a forked datascript — see `research-logseq-db-format.md`), with fts5 side-DB for search and `client-ops` side-DB for RTC sync. Properties/classes/tasks are typed entities, killing the parse-fragility class of bugs and enabling views and bulk ops — at the price of an opaque on-disk format (~monthly schema minors), a lossy markdown export, and an ecosystem reset.

**Tine.** From-scratch Rust core (parsing, indexing) in a Tauri/WebKitGTK shell with a SolidJS fine-grained-reactive frontend; reads/writes Logseq OG's exact files with no import step. Built AI-assisted by one maintainer with a no-external-code-PRs policy. Fast and files-first by construction; everything ecosystem-shaped (plugins, graph view, SRS, iOS) is absent or deliberately out of scope.

**TyLog.** Flutter UI + Rust core over plaintext **Typst** files — the only one of the four whose notes are simultaneously human-readable text, structured data (`#tylog.note/task/ref-note` calls with typed fields), and a compilable typesetting program. Worker-isolate indexing, Nextcloud sync engine with ETag/conflict safety, importers converting the competition's formats into Typst. Structure sits between OG (more: typed task/note fields, compile-verifiable) and DB (less: no entity graph, no closed values), while keeping OG-class data ownership.

## Pros and cons

**Logseq OG** — Pros: maximal data ownership; mature full feature set (queries, whiteboards, SRS, PDF annotation, plugins); free DIY sync. Cons: frozen — security-only maintenance, observably idle; acknowledged corruption risk and single-writer sync; poor large-graph performance; chronically rough mobile. *Verdict: fine to stay if it already works; a dead end to invest in.*

**Logseq 2.0 DB** — Pros: best-in-field data model (typed properties, classes, closed values, views); performance at scale is a design goal; real RTC/E2EE sync substrate; company momentum (nightlies, CLI+MCP). Cons: data lock-in is structural (one-way Mirror, lossy md export, EDN needs tooling); beta regressions (whiteboards gone, SRS not migrated, plugin ecosystem reset to ~65); mobile still invite/pre-alpha; monthly schema churn under the hood. *Verdict: the future of Logseq, but early adopters pay in features and trust.*

**Tine** — Pros: fastest architecture in the field; zero-migration Logseq-file compatibility (reversible bet); native PDF annotation + sheets/kanban that OG lacks; shipping velocity. Cons: bus-factor-one, two months old, AI-generated codebase with no external code review path; no plugin compat, graph view, SRS, iOS; no own sync. *Verdict: impressive proof of demand for fast files-first Logseq; too young to depend on.*

**TyLog** — Pros: unique typeset-PDF axis (notes → publishable documents natively); strongest task engine (RRULE + reminders + time tracking); best mobile reliability posture in the field (release-grade Android + sync-conflict safety on SAF); plaintext with verifiable structure (writers must compile); import path from both Logseq generations. Cons: no block refs/transclusion or query language (depth ceiling for heavy outliner users); no extensibility story; no SRS/whiteboards/PDF annotation; single-developer, closed source — same bus-factor critique aimed at Tine applies; no E2EE sync.

## TyLog gaps & opportunities (ranked)

1. **Ship the Logseq DB importer** (plan exists: `docs/superpowers/plans/2026-08-20-logseq-db-import.md`). OG users are stranded and DB users fear lock-in — TyLog can be the exit for both. Cheap: plan is written.
2. **Positioning: "your notes are a typeset document, not a database."** No competitor can compile a note to a publishable PDF natively. Lean on it in any public material; it's the only non-replicable moat in the matrix.
3. **Query-lite, not a query language.** The field shows queries matter (all three have some), but Tine proves scoped-DSL is enough for "everyday queries." TyLog's report blocks + saved searches already cover most of this; the gap is *inline* dynamic sections inside notes. Consider extending report blocks before ever considering a DSL.
4. **PDF annotation** is Tine's proven differentiator and a natural TyLog fit (articles pipeline + reading mode already exist; annotations could be Typst data). Largest genuinely-missing user-facing feature relative to reading-centric workflows.
5. **E2EE option for sync** — age is already in the backup design (`docs/age-encrypted-backup.md`); Logseq Sync uses age too. An age-encrypted WebDAV layer would neutralize the one sync axis where Logseq DB is ahead.
6. **Block-level refs: keep saying no.** OG/Tine users expect them, but they are the single largest complexity driver in outliner codebases (uuid tracking in text, transclusion rendering, ref-integrity on edit). TyLog's note-level model + compile-checked writers is a deliberate simplicity moat; revisit only on real user demand.
7. **SRS/flashcards: defer.** Logseq DB broke its own users' SRS data in the migration; Tine skipped it entirely. Signal: low.
