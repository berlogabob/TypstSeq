# P2P sync options for TyLog

Research checked 2026-11-05 against project code and primary project/platform documentation. The recommendation is for the scratch-vault harness in P2P2; it is not approval to replace production sync.

## Recommendation

Use **iroh for the next in-app scratch-vault experiment**, with a narrowly scoped TyLog snapshot protocol and Ouisync as the fallback to evaluate if implementing that protocol is too much work. iroh provides peer connectivity and verified blob transfer while leaving the vault's file semantics under TyLog's control. That matches the requested ticket-paired snapshot experiment and the existing Rust/Flutter bridge seam. It does mean TyLog must implement the manifest, peer authorization, change selection, and safe application itself.

P2P2 should transfer only between isolated scratch vaults. Build a manifest from paths, sizes and hashes; transfer only missing/changed blobs; verify received bytes before applying them through the existing storage/sync path. Start with loopback, then Mac-to-Android on the same Wi-Fi. Record elapsed time, bytes, CPU and retry/resume behavior. Ensure Android native context is initialized before creating an iroh endpoint: [iroh's current endpoint implementation](https://github.com/n0-computer/iroh/blob/main/iroh/src/endpoint.rs) includes Android JNI-backed initialization requirements, and the project already records that its old CLI spike aborted outside Android app context. If initialization or the custom protocol is an unreasonable fit, test whether Ouisync's repository abstraction can mirror or mount the TyLog vault without weakening its conflict and deletion safeguards.

Do not promise unattended Android sync from this research. WorkManager work is deferrable, may be delayed by constraints, and can be stopped when constraints cease to hold; a continuous transfer would need an explicit foreground/lifecycle design. The [Android background-work guidance](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work) describes these constraints.

## TyLog constraints that shape the choice

- The existing sync implementation is file-oriented (`lib/nextcloud_sync.dart` and `lib/nextcloud_sync/`). It synchronizes vault paths and bytes rather than merging note fields.
- Sync already distinguishes local and remote edits, preserves conflict copies, and tracks deletion state. In particular, absence from a WebDAV listing is not itself treated as a deletion tombstone (`lib/nextcloud_sync/path_sync.dart`). A P2P layer must preserve those rules or hand changes into the existing reconciliation path.
- Android vault access can be through SAF-backed storage. Android's Storage Access Framework grants access to user-selected document trees and providers, rather than promising an ordinary filesystem path ([SAF document-provider model](https://developer.android.com/guide/topics/providers/document-provider)). A native sync engine that assumes it owns a normal directory therefore needs staging or an adapter, followed by writes through TyLog's storage layer.
- `flutter_rust_bridge` is already used in the repository (`packages/typst_flutter`); this makes a Rust transport plausible, but does not itself supply a sync protocol or Android lifecycle integration.
- The vault is about 10,000 `.typ` notes plus assets, potentially gigabytes. A whole-vault transfer is unsuitable after initial seeding; the harness should report snapshot and changed-blob costs separately.

## Options compared

| Option | Fit for TyLog | Main costs and limits | Verdict |
|---|---|---|---|
| **iroh + blobs, with a TyLog manifest** | Rust connectivity with direct QUIC, relay fallback and hole-punching; blobs provide resumable, verifiable transfer. A manifest can identify changed files without changing the note format. | This is a transport/data-transfer toolkit, not a ready-made vault sync engine. TyLog owns discovery/tickets, authorization, manifests, apply ordering, conflicts and deletion semantics. Android initialization and real-device size/CPU/battery remain unmeasured. The iroh project has split protocol crates from the core and continues to evolve its APIs, so pin and test a specific version. | **Recommended for P2P2**, since the experiment explicitly needs a ticket-paired snapshot and TyLog-controlled writes. Keep production writes out of scope. |
| **Ouisync** | Ready-made Rust file-sync library with peer discovery/NAT traversal and officially listed Dart/Flutter and Kotlin bindings; MPL-2.0. This minimizes custom transport and file-sync code. | Its repository/storage and conflict model must be fitted to TyLog's SAF access, revisions and deletion cursors. That integration is not established by the docs. The current workspace version is 0.10.2; verify release/API maturity and storage model before adoption. | **Fallback** if its repository abstraction maps cleanly to scratch and production vaults. First test a SAF-to-Ouisync round trip and conflict/deletion behavior. |
| **Syncthing embedded / Android wrapper** | Mature, general-purpose continuous file synchronization with established file conflict/versioning behavior. | The official Android wrapper is discontinued and archived (last planned release was December 2024). Embedding another engine still requires exposing a directory and reconciling its file rules with TyLog. | Do not select the Android wrapper as a new app dependency. The core remains a reference for file-sync behavior, not a turnkey TyLog integration. |
| **libp2p** | Rust implementation and modular protocols; supports QUIC, relay and hole-punching. | Lower-level than iroh/Ouisync for this use: TyLog would still assemble peer identity/discovery, authorization, blob transfer, manifest and recovery behavior. Relay paths add latency and depend on relay availability; hole-punching is not guaranteed. | Viable if TyLog needs protocol-level control that iroh cannot provide, but too much surface for the first snapshot prototype. |
| **LAN-only mDNS + HTTPS/QUIC** | Matches the common Mac/P30/A24 same-Wi-Fi case; no public relay service required and can use a small explicit snapshot endpoint. | No remote/NAT traversal; custom peer authentication, discovery, transfer, retry and snapshot protocol still required. Network changes and guest Wi-Fi isolation break discovery/connectivity. | A useful harness mode and a possible LAN-only product, not the general P2P path. Could be tested before relay features if harness scope is reduced. |
| **Automerge/Yjs or another CRDT layer** | Handles concurrent structured-document edits and distributes incremental document updates. | Changes the authoritative note model and merge semantics; it does not by itself solve SAF access or file transfer. Yjs updates converge when all updates arrive; Automerge retains conflicting property values but presents a deterministic winner. This conflicts with TyLog's current file/revision/deletion approach and would require a separate data migration/design. | Do not use for whole-vault P2P file sync. Reconsider only for a future structured collaborative editor. |

## Evidence and source notes

- iroh describes [blobs as resumable, verifiable transfer](https://www.iroh.computer/proto) and [Documents as multiwriter key-value sync](https://www.iroh.computer/proto). These are distinct building blocks, not a ready-to-run TyLog vault synchronizer. Its [1.0 roadmap](https://www.iroh.computer/roadmap) records the split of blobs, docs and gossip into separate protocol crates. An [October 2026 security notice](https://www.iroh.computer/blog/iroh-blobs-push-fix) documents a recent push authorization bug and affected versions; pin a fixed release and test write authorization explicitly.
- Ouisync's [developer page](https://ouisync.net/developers/) describes peer discovery, NAT traversal, Rust implementation, Dart/Flutter and Kotlin bindings, and MPL-2.0. Its [source repository](https://github.com/equalitie/ouisync) describes the library and CLI; the current [workspace manifest](https://github.com/equalitie/ouisync/blob/master/Cargo.toml) sets version 0.10.2 and MPL-2.0. API stability and SAF suitability need a prototype rather than inference from feature lists.
- The [Syncthing Android repository](https://github.com/syncthing/syncthing-android) says the app is discontinued and archived. Syncthing's [sync behavior documentation](https://docs.syncthing.net/users/syncing) explains its conflict handling; its semantics should not be assumed to match TyLog's.
- libp2p's [connectivity guide](https://libp2p.io/docs/standalone-connectivity/) describes mobile carrier NAT, relay reservations and hole punching. The [hole-punching guide](https://docs.libp2p.io/concepts/hole-punching/) also explains that relay connections are limited and direct connectivity is not guaranteed.
- Android's [SAF documentation](https://developer.android.com/guide/topics/providers/document-provider) describes document trees and provider-mediated access. Its [WorkManager constraints](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work) show why “background P2P sync” needs a measured lifecycle design.
- [Yjs update semantics](https://docs.yjs.dev/api/document-updates) document commutative, associative and idempotent updates. [Automerge conflict behavior](https://automerge.org/docs/reference/documents/conflicts/) documents retained concurrent property conflicts and deterministic display choice.

## Staged plan

1. **P2P2, isolated harness:** initialize Android networking context before endpoint creation; pair two instances by short-lived ticket; transfer a scratch-vault snapshot and changed blobs. Test loopback and Mac-to-Android on LAN. Report elapsed time, exact bytes, CPU, retries/resume, and all output hashes. No writes to production vaults.
2. **Storage/reconciliation proof:** exercise scratch copies with simultaneous edits, remote and local deletion, interrupted transfer, invalid/hash-mismatched data, and SAF provider reads/writes. Apply only via TyLog's storage and reconciliation rules. Preserve originals until verified apply succeeds.
3. **Reachability and lifecycle:** repeat on different networks, including relay-required cases; measure battery and foreground/background behavior on P30/A24. Treat periodic WorkManager execution as opportunistic, not a real-time guarantee.
4. **P2P3 decision:** compare measured cost and maintenance against Nextcloud/WebDAV. Choose go/no-go and a product scope; do not enable real-vault P2P until conflict, deletion, recovery and device lifecycle gates pass.

No transfer throughput, Android battery cost, complete SAF compatibility, or production safety claim is established by this options report. Those are harness acceptance measurements, not facts to infer from vendor documentation.
